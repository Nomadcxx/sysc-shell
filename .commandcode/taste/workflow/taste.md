# Workflow Preferences

- Writes dated design docs and implementation plans under `docs/plans/` before coding and expects the agent to read them first, then implement the plan. Confidence: 0.9
- Wants `.md` handover documents for handing work to another agent, including context not in the design/plan (key decisions, session history), and asks for the absolute path to each generated doc. When a session ends with executed-but-unverified work, the handover also commissions the follow-on order: an audit (findings filed in bd as `discovered-from` the tracking issue) that the next agent starts BEFORE the owner-approved live/deploy testing. Confidence: 0.85
- Cross-agent coordination summaries: with several agents running concurrently on the repo, the user asks for a paste-ready summary addressed to the other agent's session (e.g. the one implementing MPRIS) so it knows the canonical work exists and what gates what. The summary must foreground: where the in-flight branch/worktree lives and its commit/WIP state with a "coordinate before editing / don't start a second branch" warning, what already exists so it isn't rebuilt, tracker-state traps (bd closed ≠ merged — code can sit only on the branch), the dependency/gate chain (landing media-page unblocks stacking), and the branch's binding constraints (test gates, go.mod freeze, commit-msg hook rules). Confidence: 0.6
- Audit commissions are written as a dedicated self-contained .md the receiving agent can pick up cold: the audited branch/worktree path with commit count and a full commit map, each work layer's contract documents, the method (spec walk plus verifying TDD claims — a test that passes against a stub pins nothing), explicit "points to confirm beyond the spec walk", recorded deviations framed as items for the audit to rule on (not re-litigate), the exact gate set, and a do-not list (no merge, no deploy/restart, no editing handover/research docs — findings go to bd as `discovered-from` the tracking issue; mechanical fixes land directly on the branch as commits with their own failing-first tests, structural issues go back to the owner). Verdicts use a fixed vocabulary — merge-ready / merge-ready with named corrections applied / corrections required — with every finding's bd id listed; a finding is not a failure and a green pass is a valid verdict. Confidence: 0.7
- Uses `bd` (beads) for project/task tracking and expects tracking to stay in sync. Confidence: 0.85
- Work selection is triage-driven: sessions start by investigating the next open/claimable bd issue — survey `bd ready` and `bd blocked`, pull `bd show` details on each candidate, and compare options (e.g., owner-gated live tests vs autonomous code work) before committing to one. Confidence: 0.7
- The bd tracker alone is not enough for prioritization: when picking what's next, cross-check milestone/roadmap docs, README, and other documentation (docs/plans register, handover docs encode a "commissioned order"), and reconcile those claims against actual repo state (branch merge status, conformance/scan tests enumerating remaining scope) before recommending. Confidence: 0.85
- Expects each tranche of work to happen in a dedicated git worktree + feature branch, merged to main only when it is "safe to do so" (nothing lost); the owner initiates this with an explicit "assess whether this branch is safe to merge" ask before any merge. Confidence: 0.9
- Insists on researching prior art before proposing a design — specifically DMS/DankMaterialShell and Noctalia — and treats visual/pixel parity with them as the minimum bar. Confidence: 0.9
- Requests review gates: a spec-compliance review and a code-quality/production-readiness review, each classified Critical / Important / Minor, and wants an over-engineering/YAGNI pass ("smallest diff", "lean already, ship"). Confidence: 0.85
- Distrusts agent self-reports; wants claims verified against the actual diff/code, and wants live results reported honestly rather than invented. Confidence: 0.8
- Dislikes slow TDD loops: often explicitly says to skip/avoid TDD and just make the change, though sometimes asks for TDD — so TDD only when requested. Confidence: 0.7
- Does not want the live shell started/stopped or tested in a live environment unless explicitly asked. Confidence: 0.75
- When the user directs new work (rather than selecting it from the tracker), the expected opening sequence is: audit the affected surface first, open a bd issue capturing the audit findings with acceptance criteria, then cut a dedicated worktree branched off main before touching any code. Confidence: 0.8
- When dispatching parallel/subagent work, prefers one subagent per task. Confidence: 0.6
- Runs concurrent AI coding sessions (e.g., Claude) on the same repo; a session can go parked mid-edit (e.g., quota-blocked) while still owning its work. Before claiming or starting a task, verify what's in flight — `git worktree list` plus a per-worktree dirty-state check, and `bd list --status in_progress` with ownership — and do not touch dirty parked worktrees or issues claimed by other sessions; prefer untouched slices that collide with nothing. Confidence: 0.8
- Plan documents follow the repo's established plan format — a "REQUIRED SUB-SKILL: superpowers:executing-plans" header for Claude, a Goal/Architecture/Tech Stack preamble, and numbered tasks that each begin with failing checks — and carry no Markdown task checkboxes: task status lives in bd, not in the doc. Confidence: 0.65
- Every new design/plan doc gets a dated row in the docs/plans/README.md register. Confidence: 0.7
- Consolidates duplicate divergent tables/mappings (e.g. three condition-word tables and two icon mappings for the same weather codes) into a single canonical shared source — one fact, one home. Confidence: 0.6
- `bd` is the only tracker: no session todo list (a skill's TodoWrite guidance is overridden by the repo's AGENTS.md), and work is claimed in bd (issue set in_progress) before implementation starts. Confidence: 0.7
- `bd export` has a known clobber trap — it rewrites `.beads/issues.jsonl` with only the issues it thinks changed (observed 253→1 lines). Before committing any tracker state, verify the JSONL line count against the DB issue count and, on clobber, run the documented recovery: `sqlite3 .beads/beads.db "DELETE FROM export_hashes;"` followed by a full re-export. Confidence: 0.75
- When a previously-green test package fails during execution, first establish whether the failure is pre-existing or flaky — re-run it and run the failing test against main — before treating it as a regression of the change; if it is a real regression (e.g. a leaked goroutine), fix it before moving on. Confidence: 0.65
- Pull-request descriptions for this repo enumerate the executed tasks with commit hashes, explicitly mark gated/deferred work as deliberately absent (naming the bd issue that gates it), and carry a test-plan checklist that separates green automated gates from owner-deferrable live checks. Confidence: 0.55
- When asked to summarise completed work, the user wants more than the executed-task list: the agent's own read of what it implemented, a map of how each piece is consumed within the system (which components/surfaces consume what, and what surface is deliberately dead until a later task lands), and direct yes/no answers to feature-scope questions rather than deferrals. Confidence: 0.7
- When asked for a session summary, structure it as an honest accounting with three parts: what landed, how it was implemented, and an explicit assessment of how the work does or does not address the stated goal/objective — closing with the honest gaps (deliberately deferred scope, judgment calls awaiting the owner's eyes, work not yet shipped or visually verified) rather than presenting the session as complete. Confidence: 0.55
- Work summaries should close with an explicit, graded parity verdict against Noctalia v4 and DMS — what reached parity, what is partial (naming the specific missing pieces), and what is absent — stated bluntly rather than glossed. Confidence: 0.7
- The owner's laptop is the remote live-test machine, reachable at `ssh -p 7777 nomadx@192.168.0.64` (key-based, BatchMode works); when the owner asks for a deploy/live test, it targets that host. Confidence: 0.8
- Personal/user-specific values (e.g., the owner's location coordinates for a weather config) are the owner's decision: ask the owner — or record them as an open input in a handover that tells the next session to ask — rather than scraping them from other tools' configs. The 2026-09-15 weather session was redirected by the owner precisely while mining DMS/Noctalia configs for coordinates, and the resulting handover makes the coordinates an owner-supplied input. Mining other configs may still be acceptable for genuinely technical facts, not personal data. Confidence: 0.55

- When a feature needs user-specific data (e.g., weather coordinates for a machine's config), mine the user's other tools' configs and caches — DMS/DankMaterialShell and Noctalia under `~/.config`, plus `~/.cache` and `~/.local/state` — for the real values instead of inventing placeholders. Confidence: 0.5

- When commissioned work has genuine scope decisions (implement now vs defer, which variant, which rendering primitive), surface them to the owner as multiple-choice questions with a recommended option and the trade-off stated — before fixing the design — and record the confirmed calls explicitly in the design/plan (an "Owner decisions" section). Confidence: 0.7
- Before designing, decompose codebase exploration into focused parallel explore agents (one per question — e.g. page architecture, image pipeline, text/animator primitives), each briefed to return concrete file:line references; the design then stands on those cited findings rather than memory. Confidence: 0.6
- Design docs follow a house format too: dated header with commissioning context, Goal and scope (In/Out), numbered decisions D1–Dn, Risks, and a Sources list; implementation plans reference decisions by their D-number. Confidence: 0.65
- After the design and plan are committed to main but before any product code, pause for the owner's audit and point the review at the contentious decisions explicitly — where the design deviates from reference-shell behavior, which choices are genuine owner calls, which tunables remain open. Confidence: 0.6
- When a needed upstream asset cannot be fetched or verified (e.g. the pinned Material Symbols TTF for a font rebuild), block the task visibly and report it rather than substituting something of unknown provenance. Confidence: 0.6
- Stay scoped to the question actually asked: when the user asks "what's next", answer directly from the roadmap/plans and stop — do not wander into tangents (e.g. branch hygiene for other features' work) that were not asked about; uncommissioned work is "not your concern at this stage". Confidence: 0.85
- Do not delete or discard prior sessions' working features when rebuilding — building fresh is fine, but existing user-facing capabilities (e.g. the standalone panel opened by right-clicking its bar icon) must be carried forward unless the owner explicitly approves their removal. Confidence: 0.85
- Long-duration manual tests (e.g. a 60-minute idle test) are deferred at the owner's discretion: don't track them as blockers or gates — the owner runs them later when convenient. Confidence: 0.85
- End-of-tranche close-out rule: if enough work remains, generate a handover .md (what's been done + what SHOULD be implemented to finish, for another agent to action); if not enough remains, close the work as done ensuring nothing is lost — then do housekeeping/bookkeeping to get the docs and tracker in order before moving on. Confidence: 0.8
- When the user asks whether a given piece of work was ever started/completed — usually opened as a half-remembered "my understanding is…" hypothesis — treat the recollection as a claim to verify, not a premise. The expected investigation sweep: bd (`ready`/`blocked`/`list` grep/`show` on candidates), the plans register and the specific design+plan docs (including task checkbox state), worktree list + branch names + commit-message grep, a code grep for the feature's own symbol across main AND every worktree (including in-flight feature ones), and the merge status of the plan's named dependencies. Answer by bluntly splitting the recollection into right/wrong parts, separating designed → planned → started, stating why it hasn't started (the dependency chain), and offering a concrete next action (e.g. a placeholder bd issue so dependency-queued work can't be silently lost). Confidence: 0.6
- When asked what an in-flight feature branch currently contains ("what has been developed?"), answer from direct repo evidence, not the plan doc's claims: branch delta vs main (`log main..HEAD`, merge-base, `diff --stat main...HEAD`, `status --short`), then report in layers — branch state (commits ahead, base, insertions, dirty WIP), committed work mapped task-by-task against the plan with bd ids and commit hashes, uncommitted WIP (which task it implements plus any plan-exceeding amendments), and remaining scope (gates, tracker closes, rebase onto a moved main). Flag tracker/code visibility mismatches (e.g. bd issues closed while their code still sits only on the branch), and close by explicitly correcting anything said earlier in the session that fresh evidence contradicts. Confidence: 0.55
